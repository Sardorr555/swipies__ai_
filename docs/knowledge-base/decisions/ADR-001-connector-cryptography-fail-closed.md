# ADR-001: Fail-Closed криптография коннекторов и связка ключей (Keyring)

- **Статус:** Принято (Accepted)
- **Дата решения:** 14 октября 2026 года
- **Автор:** Swipies Security / Sardor
- **Связанные коммиты:** `782f74d46`, `c407eb409`, `3bb88c257`
- **Затронутые модули:** [api/utils/key_crypto.py](../../api/utils/key_crypto.py), [internal/utility/crypto.go](../../internal/utility/crypto.go), [docker/.env.example](../../docker/.env.example)

---

## 1. Контекст и проблематика

Исторически в репозитории RAGFlow и конфигурационном файле `docker/.env:295` присутствовал дефолтный статический мастер-ключ:
`RAGFLOW_SECRET_KEY=ragflow_single_global_instance_master_secret_2026`.

При развертывании системы без явного переопределения переменных окружения возникала критическая уязвимость:
1. Любые учетные данные внешних коннекторов (токены LLM, пароли баз данных) шифровались общеизвестным статическим ключом.
2. В коде отсутствовал механизм плавной смены и ротации ключей без потери доступа к уже зашифрованным данным в базе.
3. Ошибки расшифрования в ряде мест приводили к падению бэкенда либо тихому возврату пустых строк.

## 2. Рассмотренные альтернативы

1. **Альтернатива 1: Использование внешнего хранилища секретов (HashiCorp Vault / AWS Secrets Manager)**
   - *Плюсы:* Идеальное решение для Enterprise, централизованный аудит.
   - *Минусы:* Избыточная сложность для локальной разработки, Docker Compose и небольших On-Premise инсталляций. Не решает задачу «из коробки».
2. **Альтернатива 2: Использование простой симметричной функции Fernet с одним ключом**
   - *Плюсы:* Простота реализации.
   - *Минусы:* Нет поддержки ротации нескольких поколений ключей (Keyring), отсутствие HKDF-деривации ключа на основе идентификатора тенанта.
3. **Альтернатива 3: Собственная Fail-Closed связка ключей (Keyring) с AES-256-GCM и RFC 5869 HKDF (Выбрано)**
   - *Плюсы:* Автономность, отсутствие тяжелых внешних зависимостей, криптографическая стойкость банковского уровня, поддержка ротации и изолированная деривация ключей тенантов.

## 3. Принятое решение

1. **Запрет использования дефолтных ключей для шифрования (Fail-Closed):**
   - При вызове функции шифрования `encrypt_api_key` или `encrypt_field_for_tenant` производится проверка переданного ключа.
   - Если ключ равен известным дефолтным строкам (`ragflow_single_global_instance_master_secret_2026`, `insecure_default_key`, `123456...`), выбрасывается фатальное исключение `InsecureKeyError`. Операция шифрования блокируется.
2. **Режим обратной совместимости при расшифровании (Decrypt-Only Fallback):**
   - Для предотвращения сбоя сервиса при миграции существующих продуктивных баз данных, дефолтный ключ разрешен исключительно на чтение, если он явно передан в переменной `RAGFLOW_SECRET_KEYS_ROTATION`.
3. **Многоуровневый Keyring (Связка ключей):**
   - Поддержка массива ключей ротации: при чтении данных с префиксом `enc:v1:` система поочередно пробует основной ключ `RAGFLOW_SECRET_KEY`, затем ключи из `RAGFLOW_SECRET_KEYS_ROTATION`.
4. **Удаление секретов из версионируемых файлов:**
   - Из репозитория удален дефолтный ключ в боевом конфиге.
   - Добавлен защищенный шаблон `docker/.env.example` с инструкцией по генерации ключа через `openssl rand -hex 32`.

## 4. Последствия и верификация

- **Положительные последствия:**
  - Полное исключение возможности случайного запуска продакшена на дефолтных скомпрометированных ключах.
  - Безопасная процедура ротации секретов без простоя сервиса.
  - Единый криптографический стандарт для Python- и Go-слоев проекта.
- **Отрицательные последствия / Ограничения:**
  - Разработчик обязан сгенерировать валидный ключ при локальном запуске (сервер не стартует на пустом значении).
- **Верификация:**
  - Тесты `test/test_ai_infrastructure.py` (тесты криптографии, ротации и защиты от дефолтов) проходят успешно со статусом `OK`.
