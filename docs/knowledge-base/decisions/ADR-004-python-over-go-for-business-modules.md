# ADR-004: Выбор Python вместо Go для реализации бизнес-модулей CRM и агентов

- **Статус:** Принято (Accepted)
- **Дата решения:** 15 октября 2026 года
- **Автор:** Swipies Tech Lead / Sardor
- **Связанные коммиты:** `4612f87b4`, `30f1464b5`, `dfc429bb7`
- **Затронутые модули:** [agent/tools/](../../agent/tools/), [api/crm/](../../api/crm/), [internal/service/connector.go](../../internal/service/connector.go)

---

## 1. Контекст и проблематика

Проект RAGFlow представляет собой полиглотный монолит:
- **Python:** Ядро AI-агентов, парсеры документов, RAG-пайплайн, ORM Peewee, REST API на Flask/Werkzeug.
- **Go:** Модули высокопроизводительной синхронизации (`internal/syncer`), коннекторы внешних источников данных (`internal/service/connector.go`), API-сервер на Go.

При проектировании интеграционного модуля CRM/ERP возник архитектурный выбор:
*Где реализовывать адаптеры amoCRM, Bitrix24, 1С, Outbox Worker и агентские инструменты — на Go или на Python?*

## 2. Рассмотренные альтернативы

1. **Альтернатива 1: Реализация CRM-логики на Go (`internal/service/crm`)**
   - *Плюсы:* Высокая производительность параллельных сетевых запросов, строгая статическая типизация, низкое потребление памяти.
   - *Минусы:*
     1. Текущий слой Go в upstream v0.27.2 содержит незавершенные интерфейсы (`user.go:150`, `tenant_model_provider.go:62`) и тяжелую CGO-зависимость (`office_oxide.h`), что затрудняет быструю сборку и тестирование.
     2. Движок диалоговых AI-агентов (Agent Engine / Canvas) исполняется строго в Python-процессе. Вызов Go-модулей из агента потребовал бы реализации gRPC/IPC моста между Python и Go, что внесло бы существенную задержку на сетевую сериализацию.
2. **Альтернатива 2: Реализация CRM-логики на Python (`api/crm/` и `agent/tools/crm_*`) (Выбрано)**
   - *Плюсы:*
     1. Прямая нативная интеграция в реестр инструментов агентов RAGFlow (`agent/tools/`).
     2. Доступ к существующей транзакционной модели данных ORM Peewee и пулу соединений MySQL.
     3. Простота использования криптографического модуля `api/utils/key_crypto.py`.
     4. Высокая скорость разработки и независимость от состояния CGO в Go-подсистеме.
   - *Минусы:*
     1. Ограничения GIL при высокой частоте исходящих запросов (компенсировано за счет асинхронного Outbox воркера и пакетной обработки).

## 3. Принятое решение

1. **Бизнес-логика, CRM-инструменты и Outbox Worker реализуются на Python:**
   - Инструменты диалоговых агентов: [agent/tools/crm_lead_create.py](../../agent/tools/crm_lead_create.py) и [agent/tools/crm_stock_check.py](../../agent/tools/crm_stock_check.py).
   - Адаптеры интеграций: [api/crm/adapters/](../../api/crm/adapters/).
   - Очередь Outbox и аудит: [api/crm/tasks/outbox_worker.py](../../api/crm/tasks/outbox_worker.py).
2. **Слой Go используется для высоконагруженных задач передачи данных:**
   - Коннекторы синхронизации файлов и баз знаний (`internal/service/connector.go`) и криптографическая утилита (`internal/utility/crypto.go`) поддерживаются в согласованном состоянии с Python-модулями.
   - В будущем, при росте нагрузки на синк документов CRM (выгрузка сотен тысяч номенклатурных позиций 1С в векторный индекс), задача тяжелого синка будет вынесена в Go Syncer.

## 4. Последствия и верификация

- **Положительные последствия:**
  - Нулевая задержка вызова инструментов агентом внутри Python-процесса.
  - Мгновенная готовность к развертыванию в основном Docker-контейнере API.
  - 100% покрытие тестами через стандартный `unittest` / `pytest`.
- **Верификация:**
  - Тест `test/test_crm_system.py` запускается за 0.8 секунд и проверяет всю цепочку без внешних сервисов и IPC-мостов.
